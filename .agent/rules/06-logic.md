## 1.Optimistic UI Updates (楽観的UI更新)
概念: サーバーからのレスポンスを待たずに、UIを更新すること。
GearPitでの適用: ギアの重量を「150g」から「145g」に書き換えた瞬間、保存中であっても画面上の「総重量」は即座に -5g され、グラフも再描画されるべきです。


## 2.Flat Data, Rich Views (データはフラットに、表示はリッチに)
概念: DB上では Gear と Loadout は多対多の単純な関係で保存し、深い階層構造（JSONのネストなど）は避ける。
GearPitでの適用: 「夏山セット」の中に「救急ポーチ」を入れるような「キット・イン・キット」を作りたくなりますが、DB構造が複雑化します。DBはフラットに保ち、UI上でグルーピング表示（Accordionなど）するのが正解です。

## 3."Draft" State (下書き保存)
概念: Tripの計画中は、いちいち「保存」ボタンを押させない。
GearPitでの適用: Trip作成画面では、変更があるたびに localStorage またはURLパラメータ（nuqs）に状態を保存し、ブラウザを閉じても作業を再開できるようにします。

## 4.Base Unit Storage (基本単位での保存)
概念: 単位（kg, g, oz）は表示上の装飾に過ぎない。
GearPitでの適用: DBには必ず 「グラム(g)」 または 「ミリグラム(mg)」 の整数値（Integer）で保存します。浮動小数点（Float）は計算誤差が出るため、重量計算アプリでは避けるのが鉄則です（Rustの u32 などが最適）。
